# [004] SQL 注入安全审计与攻击实测

- 日期：2026-10-13
- 状态：已完成
- 涉及端：server
- 关联：[006-Sequelize-ORM迁移](006-Sequelize-ORM迁移.md)（本审计结论是 ORM 迁移的输入之一）

## 需求点

- 服务层存在大量直接 SQL 拼接，需确认**是否存在 SQL 注入面**，并给出结论与加固建议。

## 审计结论：无注入面

对全库 **36 处** SQL 模板插值逐处分类核实：

| 类别 | 数量 | 做法 | 结论 |
|---|---|---|---|
| 动态 WHERE 拼接（`where += ' AND status = ?'`） | 14 | 值一律 `args.push(值)` 走 `?` 占位符 | 安全 |
| `SET ${fields}` / `IN (${...})` | 9 | 字段名是代码内字面量；占位个数用 `map(() => '?')` 生成，值全 `?` | 安全 |
| `${table}` / `${where}` 片段 | 13 | table 只传 `'workers'/'users'` 等字面量（调用方已核实）；where 是上面拼的片段 | 安全 |

- 危险写法（模板直插用户输入 `` `...${req.query.x}` ``）：**全库 0 处**。
- 原理：`?` 占位符走 mysql2 参数化查询，注入串进去只会变成**被搜索的纯字面量**，不会成为 SQL 语法。

## 攻击实测（真实 HTTP + 查库核对）

| 攻击串 | 接口 | 结果 |
|---|---|---|
| `keyword=';DROP TABLE workers;--` | 订单列表 | HTTP 200，纯文本匹配 0 命中 |
| `status=pending' OR '1'='1` | 订单列表 | HTTP 200，枚举校验 + 参数化，无泄漏 |
| `keyword=%25`（通配符注入） | 订单列表 | 200，返回全部（LIKE `%` 预期行为，非注入） |

实测后查库：**8 张表完好、workers 5 行无损**。

## 关键决策

- **不为防注入引入 ORM**（当时结论）：参数化原生 SQL 已安全，复杂 JOIN / 乐观锁 CAS / `FIELD()` 排序用原生表达最直接。
- 后续（同日）用户从**可维护性**角度决策引入 Sequelize → 见 [006](006-Sequelize-ORM迁移.md)；ORM 迁移后兜底查询仍必须走 `replacements` 参数化。
- 可选加固（低优先，未实施）：restrict 表名白名单、CAS 字段白名单、status 枚举校验。

## 验证记录

- 注入串 ×3 打接口全 200；`SHOW TABLES` 8 张表 + `COUNT(workers)=5` 复核无损。
